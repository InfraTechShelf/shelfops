### 接続ワーカーの分離（フェーズ3）

別資格情報モードには、同一プロセス内で先に別アカウントで接続すると
認証済みHTTP接続が再利用され**指定した資格情報が無視される**不具合があった
（[docs/SPEC_phase2.md](docs/SPEC_phase2.md) §4.6、実環境で原因確定）。

接続プールはプロセス単位なので、**DDCへの接続を資格情報ごとに別プロセス
（ワーカー）へ追い出す**ことで根本解決する。

- GUI（`CitrixAdminTool.exe`）はSDKを直接呼ばず、`CitrixAdminTool.Worker.exe` を起動する。
- 統合認証 … GUIと同じユーザーでワーカーを起動（`System.Diagnostics.Process`）。
- 別資格情報 … `CreateProcessWithLogonW` の netonly でワーカーを起動する。
  ワーカープロセス全体が指定資格情報のネットワークIDを持つため、
  **ワーカー内では偽装せず統合認証として接続すればよい**（フェーズ2の不具合原因が消える）。
- GUIとワーカーは一時ファイル（`%APPDATA%\CitrixAdminTool\tmp\`）でやり取りする。
  **パスワードは `CreateProcessWithLogonW` の専用引数のみ**に渡し、
  コマンドラインにも一時ファイルにも載せない。

## ビルド

この端末には .NET SDK / NuGet / .NET Framework 4.8 Developer Pack が入っていないため、
**外部パッケージを一切使わない構成**にしてある。VS BuildTools の MSBuild だけでビルドできる。

```bash
"C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\MSBuild\Current\Bin\MSBuild.exe" CitrixAdminTool.sln /p:Configuration=Release
```

成果物は `dist\Release\` に出力される。

### 外部依存を持たないための工夫

| 仕様書の想定 | 実際の実装 | 理由 |
|---|---|---|
| NuGet `Microsoft.PowerShell.5.1.ReferenceAssemblies` | GAC の `System.Management.Automation.dll` を直接参照（`Private=false`） | NuGetが無いため。このDLLはPowerShell 5.1に同梱されるWindowsの構成要素で、CVAD管理環境にも必ず存在する |
| .NET Framework 4.8 ターゲティングパック | 未インストール時のみ `FrameworkPathOverride` でランタイムのアセンブリを参照（`Directory.Build.props`） | Developer Pack が無くてもビルドを通すため。Developer Pack がある端末では通常どおり参照アセンブリが使われる |
| JSONライブラリ | `Configuration/Json/` に最小実装を自作 | Json.NET等を持ち込まず、単一フォルダ自己完結を守るため |
| WPFのアセンブリ（フェーズ2） | ランタイム配下の `WPF\` を `HintPath` で直接参照（`Private=false`） | ターゲティングパックが無いと既定の参照解決では見つからないため。XAMLのマークアップコンパイルもランタイム配下の `PresentationBuildTasks.dll` で成立する |
| MVVMフレームワーク | `Mvvm/` に最小実装を自作 | 同上 |

Citrix のモジュール／スナップインは**実行時に動的ロード**するので、
ビルド時にCitrixアセンブリは不要。したがってビルドはこの環境で完結する。

### 1. フォルダをコピーする

`dist\Release\` を**フォルダごと**CVAD管理環境へコピーする。
インストーラも管理者昇格も不要。標準ユーザー権限で動く。

コピーされるファイルはこれだけ:

```
CitrixAdminTool.exe                 ← GUI版
CitrixAdminTool.exe.config
CitrixAdminTool.Worker.exe          ← 接続ワーカー（GUIが起動する。単体では使わない）
CitrixAdminTool.Worker.exe.config
CitrixAdminTool.ConsoleTest.exe     ← コンソール版
CitrixAdminTool.ConsoleTest.exe.config
CitrixAdminTool.Core.dll            ← 全実行ファイルが共用する接続層
CitrixAdminTool.pdb / .Worker.pdb / .ConsoleTest.pdb / .Core.pdb  （任意。行番号用）
```

GUI版・接続ワーカー・コンソール版を併置している。
**`CitrixAdminTool.Worker.exe` はGUIが内部で起動するもので、直接実行しない。**
GUIと同じフォルダに存在する必要がある（GUIは自分と同じ場所からワーカーを探す）。
コンソール版は終了コードを返すのでバッチからの定期疎通チェックに使え、
GUIが起動しない環境の切り分けにも役立つ。

## GUI版の使い方（フェーズ2）

`CitrixAdminTool.exe` を実行する。

```
┌────────────────────────────────────────────────────────────┐
│ [接続テスト] [全サイト接続テスト] │ [保存] │ [設定フォルダ] [ログフォルダ] │
├──────────────┬─────────────────────────────────────────────┤
│ サイト一覧    │ サイト設定（ID / 表示名 / DDC / 認証モード） │
│ ○ 東京本番   ├─────────────────────────────────────────────┤
│ × 大阪DR     │ 接続結果                                      │
│ [追加][削除] │                                              │
├──────────────┴─────────────────────────────────────────────┤
│ ステータス                                      [進捗バー]  │
└────────────────────────────────────────────────────────────┘
```

- 一覧の記号は接続状態（○ 成功 / × 失敗 / … 実行中 / − 未実行）。
- **代替DDCは1行に1台**。改行・カンマ・セミコロン区切りを受け付ける。
- 未保存の変更があるとタイトルバーに `*` が付き、終了時に確認する。
- 接続テストは非同期実行なので、実行中も画面は固まらない。
- 結果はコンソール版と同じ書式のテキストで表示され、同じ内容が
  診断情報付きでログファイルにも書き出される。

### 別資格情報モード

サイトの認証モードを「別の資格情報（接続時に入力）」にすると、
接続のたびにダイアログでアカウントを入力する。

- 入力内容は**保存されない**。`sites.json` に書かれるのは `authMode` だけ。
- 指定したアカウントは**ネットワーク認証にのみ**使われる
  （`runas /netonly` と同じ挙動。ローカルの識別子は変わらない）。
- そのためパスワードの誤りはローカルでは検出されず、
  DDCへ接続した時点で認証エラーになる。

設計の背景は [docs/SPEC_phase2.md](docs/SPEC_phase2.md) §4 を参照。

### 設定ファイルの保存先に注意

| 版 | 読み書きする場所 |
|---|---|
| GUI版 | `%APPDATA%\CitrixAdminTool\sites.json` |
| コンソール版 | 実行フォルダ直下の `sites.json` |

仕様書§9.2の定めどおりだが、両方を同じフォルダに置くため保存先が食い違う。

GUI版は起動時、ローミング側が無ければ**実行フォルダ側の `sites.json` を読み込む**ので、
フェーズ1で作った設定をそのまま引き継げる（保存するとローミング側に書かれる）。

逆にGUI版で編集した設定をコンソール版に使わせたい場合は、パスを明示的に渡す:

```bash
CitrixAdminTool.ConsoleTest.exe "%APPDATA%\CitrixAdminTool\sites.json"
```

GUI版のログは `%APPDATA%\CitrixAdminTool\logs\` に出る（「ログフォルダ」ボタンで開ける）。

## コンソール版の使い方（フェーズ1）

### 1. 初回実行 — 設定ファイルのひな形を作る

```bash
CitrixAdminTool.ConsoleTest.exe
```

`sites.json` が無ければ、記入例入りのテンプレートを同じフォルダに作って終了する。

### 2. sites.json を編集する

メモ帳などで開き、実際のDDCのFQDNに書き換える。

```json
{
  "sites": [
    {
      "id": "site-tokyo-prod",
      "displayName": "東京本番サイト",
      "primaryDdc": "ddc01.corp.example.com",
      "alternateDdcs": ["ddc02.corp.example.com"],
      "authMode": "IntegratedWindows"
    }
  ]
}
```

- `primaryDdc` から順に試し、失敗したら `alternateDdcs` へフェイルオーバーする。
- `authMode` は**コンソール版では `IntegratedWindows` のみ**対応。
  `PromptForCredential` のサイトは、資格情報を集める手段が無いことを明示して失敗する
  （黙って統合認証にフォールバックしない。誰の権限で操作したかを偽らないため）。
  別資格情報を使う場合はGUI版を利用する。
- **資格情報は絶対に書かない**。ツールも保存しない。
- 手編集しやすいよう、`//` コメントと末尾カンマを許容している。

### 3. 再実行して結果を得る

```bash
CitrixAdminTool.ConsoleTest.exe
```

出力例:

```
[開発サイト]
  → ddc01.test.local ... OK (Site: TESTDDC, Ver: <ControllerVersionの値>, 1.9s)
    認証: TEST\administrator
    機能レベル: <DefaultMinimumFunctionalLevelの値>
    SDK : Module
```

サイト名・DDC・認証ユーザー・SDK・所要時間は 2026-08-10 の実測値。
`Ver` と `機能レベル` は今回の修正で追加した項目のため、次回実行で値が入る。

同じ内容が `ConnectionTest_yyyyMMdd_HHmmss.log` にも書き出される。
**このログを開発環境へ持ち帰って分析する。**

### コマンドライン引数

```
CitrixAdminTool.ConsoleTest.exe [sites.jsonのパス] [-v|--verbose]
```

- パス省略時は実行ファイルと同じフォルダの `sites.json`。
- `-v` は詳細な診断情報（スタックトレース、PowerShellの警告など）を画面にも出す。
  **指定しなくてもログファイルには必ず全部記録される**ので、通常は不要。

### 終了コード

| コード | 意味 |
|---|---|
| 0 | 全サイト接続成功 |
| 1 | 失敗したサイトあり |
| 2 | 設定ファイルが無いのでテンプレートを作成した |
| 3 | 設定ファイルが読めない／不正 |
| 4 | 想定外のエラー |

| 設定ファイル未配置時のテンプレート生成 | 実環境でも正常動作（終了コード2） |
| 接続失敗時のエラー内容 | 名前解決失敗まで内部例外チェーンで追跡できることを確認 |

`Get-BrokerController` は追加の権限を要さず通り、`DNSName` による接続先DDCの
特定にも成功した（一致しなかった場合に出る「先頭のコントローラを使用します」の
警告がログに無いことで確認）。

**機能レベル `L7_9` について** … これはサイトが新規デリバリーグループ／カタログに
与える*既定の*最小機能レベルであり、コントローラ本体（7.45系）より世代が古い。
個々のデリバリーグループは自身の `MinimumFunctionalLevel` を持つため、
この値がそのままサイト全体の制約になるわけではない。ただしフェーズ2で
機能レベル依存のBroker操作を実装する際、既定値がこの世代である点は前提として効く。

#### `Get-BrokerSite` は製品バージョンを返さない

返却プロパティを全件ダンプして確認した結果、`ControllerVersion` / `Version` /
`ProductVersion` / `DesktopStudioVersion` はいずれも**存在しなかった**。
バージョンらしき名前は `InMemorySchemaAppliedVersion`（内部スキーマ版）のみで、
これは製品バージョンではない。

そこで実装を次のように変更した。

- **製品バージョン** … `Get-BrokerController` の `ControllerVersion` から取得する。
  サイト内の全コントローラが返るため、接続先DDC自身のものを `DNSName` で選ぶ
  （混在バージョン環境で誤った値を出さないため）。
- **機能レベル** … `Get-BrokerSite` の `DefaultMinimumFunctionalLevel` を併せて表示する。
  製品バージョンとは別物だが、どの世代のBroker機能が使えるかの判断材料になる。
- バージョン取得は**補助情報の扱い**とし、失敗しても接続は成功のまま報告する。
  Citrix管理者ロールの権限差で `Get-BrokerController` だけ通らない可能性があるため、
  バージョンが取れないことを理由に「接続失敗」と報告してはいけない。

#### フェイルオーバーの実動作（受け入れ基準④）

存在しないDDCをプライマリに、実在するDDCを代替に置いて確認した。

```
[フェイルオーバー検証]
  → ddc-nonexistent.test.local ... FAILED (1.8s)
  → ddc01.test.local ... OK (Site: TESTDDC, Ver: 7.45.1100.0, 0.3s)
  ** プライマリDDCが失敗したため代替DDCへフェイルオーバーしました。
```

`GetDdcsInTryOrder()` の順序どおりに試行し、最初に成功したDDCで確定している。

#### 所要時間の内訳 — フェーズ2の常駐Runspace化に向けた実測

同一プロセス内で、**1回目の試行が 1.8〜3.2秒、2回目以降が 0.3秒**という差が
一貫して観測された。上のフェイルオーバー検証がその典型で、
失敗した1回目が1.8秒、成功した2回目が0.3秒である。

Runspaceは試行ごとに使い捨てているのでCitrixモジュールは毎回ロードし直しているが、
それでも2回目が速い。差の主因はプロセス単位で一度きり発生するコスト
（アセンブリロード、JIT、WCFスタックの初期化）と考えられる。

つまり**現在の所要時間の大半は初回のウォームアップであり、
DDCとの通信そのものは0.3秒程度**ということになる。
仕様書§13が挙げる常駐Runspace管理への移行は、
GUI化して操作を連続実行するフェーズ2で効いてくる見込みが立った。

なお、失敗側の1.8秒にはDNSの名前解決失敗の待ち時間も含まれるが、
初回オーバーヘッドと分離できていないためDNS単独の寄与は不明。
「到達はするがサービスが停止している」DDCではWCFのタイムアウト待ちで
さらに長くなる可能性があり、フェイルオーバーの実用性に関わる。
必要になった時点でタイムアウト設定の追加を検討する。

### 別資格情報モードに不具合が見つかった（2026-08-11・調査中）

2026-08-10の時点では「動作した」と判断したが、**それは誤りだった**。
翌日の追加検証で、**存在しないアカウント名 `test.local\Administrator1` を入力しても
接続が成功する**ことが判明した。

```
実行ユーザー   : TEST\CLAdmin              ← プロセスを起動したアカウント
  → ddc01.test.local ... OK (Site: TESTDDC, Ver: 7.45.1100.0, 0.1s)
    認証: test.local\Administrator1        ← 存在しないアカウント。なぜか成功
```

実際には3回とも `TEST\CLAdmin` で認証されていたと考えられる。
つまり**指定した資格情報は使われていない**。

#### なぜ気づけなかったか

`GetEffectiveUserName()` が**入力された値をそのまま返していた**ため、
偽装が効いていようがいまいが「認証: <入力したアカウント>」と表示されていた。
「誰の権限で操作したかを偽らない」ことを意図した実装が、
皮肉にも逆方向に働いて**検証不能な表示**を作っていた。
誤った資格情報を試すまで発覚しなかったのはこのためである。

#### 原因の見立て

ローカルでの再現テストにより、当初疑った「PowerShellのパイプラインが別スレッドで動くため
偽装が引き継がれない」という仮説は**否定された**。パイプラインは別スレッドで動くが、
.NETのExecutionContextが偽装を伝播しており、偽装自体はコマンドレットまで届いている。

有力なのは **.NET のHTTP接続プールの再利用**である。3回の検証はいずれも
同一プロセス内で「先に統合認証で `ddc01.test.local` へ接続成功 → その後に別資格情報で接続」
という順序になっており、認証済みのHTTP接続が再利用された可能性が高い。

`LOGON32_LOGON_NEW_CREDENTIALS` は**ローカル識別子を変えない**ため、
System.Net / WCF が接続プールのグループ名を `WindowsIdentity` から決めている場合、
統合認証時と別資格情報時とで**同じグループとみなされてしまう**。
これが事実なら、プロセス内で識別子ベースの分離を試みても解決しない。

#### 現時点の対処（暫定）

不具合そのものは未修正だが、**誤った報告をしない**ようにした。

- 「認証:」の1行を廃止し、**確認できた事実**（プロセス実行ユーザー）と
  **指定値にすぎないもの**（指定した資格情報）を分けて出す。
- コマンドレット実行時にスレッド偽装トークンが有効だったかを毎回記録する
  （`WindowsIdentity.GetCurrent(true)` の有無。ローカル識別子は変わらないため
  これでしか判別できない）。
- 「DDCが実際にどちらのアカウントを認証したかは確認できない」旨と
  既知の問題を結果に明示する。

**この状態の別資格情報モードを、権限分離が必要な用途に使ってはいけない。**

なお統合Windows認証の側はこの問題の影響を受けない（指定と実際が一致するため）。

### 所要時間 — 常駐Runspace化の裏づけが増えた

同一プロセス内で 3.3秒 → 0.1秒、0.5秒 → 0.1秒 と、フェーズ1と同じ
「初回だけ遅い」パターンが再現した。DDCとの通信自体は0.1〜0.5秒で、
残りはプロセス単位で一度きり発生するウォームアップである。

      代替で成功する経路はGUIでは通っていない。コンソール版では実証済みで、

### 切り分けテストの結果（2026-08-11）— 原因確定

実環境で5回の実行を行い、ログを分析した。

| 時刻 | 認証 | ddc01.test.local の結果 |
|---|---|---|
| 00:39:51 | 別資格情報 `AdminTest`（誤った資格情報） | **認証エラーで失敗**「呼び出し元はサービスによって認証されませんでした」 |
| 00:40:29 | 統合認証（CLAdmin） | 成功 |
| 00:40:53 | 別資格情報 `Administrator`（正） | 成功 |
| 00:42:06 | 統合認証（CLAdmin） | **認可エラーで失敗**「不十分な管理者権限」 |
| 00:42:22 | 別資格情報 `Administrator`（正） | **成功** |

**1本目が切り分けの本体。** プロセスを完全に終了してから新規起動し、
最初の操作として誤った資格情報で接続した結果、DDC側の認証で正しく拒否された
（`SecurityNegotiationException` / 偽装トークン=あり）。
「LogonUserはローカルで検証せず、DDC接続時に初めて認証エラーになる」という
設計どおりの箇所で失敗している。

**原因はプロセス内の認証済み接続の再利用と確定。**
偽装のメカニズム自体は機能しており、新規プロセスなら指定した資格情報が
実際にネットワーク認証へ使われる。同一プロセス内で先に別のアカウントで
接続していた場合にのみ、その接続が再利用されて資格情報が無視される。

**4〜5本目は権限分離の実証としても価値がある。**
CLAdmin（Citrix管理者ロールを外した状態と推察）は認証は通るが
**認可**で拒否され、直後にAdministrator指定では成功した。
資格情報が実際にDDCへ届くとき、Citrix Delegated Administrationによる
権限差が期待どおり効くことを示している。

**ログ設計の教訓** … 当時のログにはプロセスIDが無く、どの実行が同一プロセスかを
タイムスタンプから推定するしかなかった。以後のビルドではヘッダに
`PID / ビット数 / プロセス起動時刻` を記録する（GUI版・コンソール版とも）。

**修正方針（フェーズ3で実装済み）: 接続プロセスの分離。**
GUI（操作するプロセス）とDDCへ接続するプロセスを分け、
接続ワーカーを**資格情報ごとに1プロセス**とする。
詳細は [docs/SPEC_phase3.md](docs/SPEC_phase3.md)。

### CVAD管理環境での検証結果（2026-08-11 / CL01）— 完了

出ていた条件そのもの（統合認証の後に別資格情報を同一セッションで実行）である。

| # | ワーカーPID | 指定アカウント | ddc01 | エラー種別 |
|---|---|---|---|---|
| 1 | 7036 | 統合認証（CLAdmin） | **OK** | — |
| 2 | 12852 | test.local\Administrator（正） | **OK** | — |
| 3 | 12744 | test.local\Administrator1（存在しない） | FAILED | **認証**エラー |
| 4 | 7652 | test.local\CLUser（実在・ロールなし） | FAILED | **認可**エラー（不十分な管理者権限） |

**3つの異なるアカウントが3つの異なる結果を返した。** これが分離の完全な実証。

- 3番（存在しないアカウント）→ **認証**エラー「呼び出し元はサービスによって

「存在しない/実在するがロールなし」という入力差をツールが正しく反映している証。

- **接続再利用バグの解消** … 同一GUIセッションで各アカウントが正しく区別された。

- **観測可能性** … どのアカウントを使ったかが全ログに明記される

これをもってフェーズ3（接続ワーカー分離）の受け入れ基準（SPEC_phase3.md §4）を

## フェーズ3+ 統合認証ワーカーの常駐化（実装済み・効果測定待ち）

最も使う統合認証ワーカーを常駐させ、複数リクエストを1プロセスで処理させることで、
2回目以降のウォームアップを省く（実測ベースで0.3秒程度が見込み）。

- **統合認証のみ常駐**。別資格情報ワーカーは安全性維持のため使い捨てのまま
  （「都度入力・非永続」「誤った資格情報は必ず失敗」を崩さない）。
- IPCは名前付きパイプ（信頼できるGUIがサーバ／現在のユーザーのみアクセス可）。
- クラッシュ回復・タイムアウト・GUI終了時の停止・孤児プロセス防止を実装。
- ログの「接続ワーカー: PID」が、常駐なら繰り返しで同一値、別資格情報なら毎回別値。
  → 開発端末で常駐・回復・停止を検証済み。詳細は [docs/SPEC_phase3.md](docs/SPEC_phase3.md) §6。

CVAD環境での効果測定の手順は [docs/検証手順.md](docs/検証手順.md) の**検証D**。

## フェーズ4 Broker管理操作（マシン一覧・メンテナンスモード切替）

接続層の上に、実際の管理操作を載せる最初の増分。
詳細は [docs/SPEC_phase4.md](docs/SPEC_phase4.md)。

- **マシン一覧（読み取り）** … `Get-BrokerMachine`。メイン画面「マシン一覧」ボタンで
  選択サイトの一覧ウィンドウを開く。デリバリーグループで絞り込み可。
- **メンテナンスモード切替（書き込み）** … `Set-BrokerMachine -InMaintenanceMode`。
  **実行前に必ず確認ダイアログ**を出し、切替後は状態を読み直して事実を返す。
- ワーカーのリクエストを「接続テスト専用」から**操作リクエスト `{op, site, params}`**
  へ一般化した。すべての操作は既存ワーカー経由（統合認証=常駐 / 別資格情報=使い捨て）で
  実行し、接続分離の安全性を保つ。
- 別資格情報サイトのマシン一覧ウィンドウは、開いている間だけ資格情報を保持
  （初回1回入力・閉じたら破棄・ディスクに書かない）。

開発端末で検証済み: 操作がワーカー経由で通ること（統合=常駐PID一定 / 別資格情報=毎回別PID）、
マシン一覧ウィンドウの生成、接続テスト等の回帰。CVAD環境での検証は
[docs/検証手順.md](docs/検証手順.md) の**検証F・G**。

## フェーズ4+ セッション操作（一覧・ログオフ・切断）

フェーズ4の操作プロトコルの上に、セッション操作を追加。
詳細は [docs/SPEC_phase4plus_sessions.md](docs/SPEC_phase4plus_sessions.md)。

- **セッション一覧（読み取り）** … `Get-BrokerSession`。メイン画面「セッション一覧」ボタン。
  ユーザー名・デリバリーグループで絞り込み可。
- **ログオフ（Stop-BrokerSession）・切断（Disconnect-BrokerSession）** … 破壊的操作。
  **実行前に必ず確認ダイアログ**（特にログオフは「未保存の作業が失われる」と強く警告）。
  対象は必ず Uid で1件取得してから `-InputObject` で渡し、取り違えを防ぐ。成否を監査ログに残す。
- **シャドウは含めない**。Brokerコマンドレットで完結せず、対象マシンへの
  リモートアシスタンス起動という別経路が要るため（次段）。

開発端末で検証済み: 操作がワーカー経由で通ること、セッション一覧ウィンドウの生成、
既存操作の回帰。CVAD環境での検証は [docs/検証手順.md](docs/検証手順.md) の**検証H・I・J**。
