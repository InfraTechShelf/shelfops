# CVAD GUI管理ツール 仕様書（フェーズ4: Broker管理操作）

## 0. このドキュメントの位置づけ

接続層（フェーズ1〜3＋）の上に、実際のBroker管理操作を載せる最初の増分。
本フェーズのスコープは **マシン一覧（読み取り）** と
**メンテナンスモード切替（書き込み）** の2つ。

以降の操作（セッション、デリバリーグループ、ポリシー、タグ等）は、
ここで確立する「操作プロトコル」の上にモジュール的に追加していく。

## 1. すべての操作はワーカー経由

管理操作も、接続テストと**同じワーカープロセス**で実行する。これは絶対条件で、
バイパスするとフェーズ2〜3で解決した安全性（接続再利用の防止・資格情報の分離）が
崩れる。

- **統合認証** … 常駐ワーカー（フェーズ3+）を使い回す。マシン一覧もメンテナンス切替も
  接続テストと同じ暖まったプロセスで動く。
- **別資格情報** … `CreateProcessWithLogonW`(netonly) の使い捨てワーカー。
  操作ごとに新プロセス。

## 2. 操作プロトコル（接続テスト専用からの一般化）

ワーカーへのリクエストを「操作リクエスト」に一般化した。

```json
{ "op": "test" | "listMachines" | "setMaintenance",
  "site": { ...サイト定義... },
  "params": { ...操作ごとのパラメータ... } }
```

レスポンスは op によって型が変わる:

| op | cmdlet | レスポンス型 |
|---|---|---|
| `test` | Get-BrokerSite / Get-BrokerController | `SiteConnectionResult`（従来どおり） |
| `listMachines` | Get-BrokerMachine | `BrokerOperationResult`（`Machines` にデータ） |
| `setMaintenance` | Set-BrokerMachine | `BrokerOperationResult`（`Message` に結果） |

- リクエストの授受は、常駐ワーカーは名前付きパイプ、使い捨てワーカーは一時ファイル。
  どちらも同じ操作リクエストを運ぶ。
- 呼び出し側（GUI）は要求した op を知っているので、対応する型でデシリアライズする。

Core側の担当:
- `Models/BrokerMachine.cs` … マシン1台のDTO。
- `Models/BrokerOperationResult.cs` … 汎用の操作結果。
- `Connection/BrokerOperationService.cs` … 操作の実体。DDCフェイルオーバー＋SDKロードを
  接続テストと共通化（`BrokerSdkHelpers`）。検証済みの `CitrixConnectionService` は不変。
- `Connection/WorkerConnectionService.cs` … GUIの窓口。`ListMachines*` / `SetMaintenance*` を
  統合認証・別資格情報それぞれで提供。

## 3. マシン一覧（読み取り）

`Get-BrokerMachine -AdminAddress <ddc> [-DesktopGroupName <グループ>] -MaxRecordCount <N>`

取得する項目（プロパティ名が揺れる可能性に配慮して候補取得）:
マシン名 / DNS名 / カタログ / デリバリーグループ / 登録状態 / 電源状態 /
集約状態 / メンテナンスモード / セッション数。

GUIでは、メイン画面の「マシン一覧」ボタンで選択中サイトの一覧ウィンドウを開く。
デリバリーグループ名で絞り込める。

## 4. メンテナンスモード切替（書き込み）★確認必須

`Set-BrokerMachine -AdminAddress <ddc> -MachineName <名前> -InMaintenanceMode <bool>`

- **書き込み操作なので、実行前に必ず確認ダイアログを出す**
  （対象マシン名とON/OFFを明示）。これはViewの責務。
- 切替後、`Get-BrokerMachine` で**反映後の状態を読み直し**て結果に含める
  （「変えたつもり」で終わらせず、事実を返す）。
- 権限が無ければ「不十分な管理者権限」で失敗する。これは正常な振る舞いで、
  フェーズ3の検証で見た**認可**の差がそのまま効く。

## 5. 別資格情報サイトでの資格情報の扱い

マシン一覧ウィンドウを開いている**別資格情報サイト**では、最初の操作時に
1回だけ資格情報を入力させ、**そのウィンドウを開いている間だけメモリに保持**する
（更新・メンテナンス切替で使い回す）。ウィンドウを閉じるときに破棄する。
ディスクには一切書かない。

これは「都度入力・非永続」の範囲内での運用上の妥協（1操作ごとに何度も
入力させると実用に耐えないため）。誤った資格情報は従来どおりDDC接続時に失敗する。

## 5.1 ログ出力（監査記録）

マシン操作もログファイル（`%APPDATA%\CitrixAdminTool\logs\`）に残す。
特にメンテナンス切替は**書き込み操作なので、成否にかかわらず監査記録として必ず記録する**
（誰が・どのアカウントで・どのマシンを・ON/OFFどちらにしたか・結果）。

- ユーザーが「更新」を押したマシン一覧取得はログを残す。
  メンテナンス切替後に内部的に走る自動更新は二重にログしない（1操作＝1ログ）。
- ログ名はミリ秒まで含める（`ConnectionTest_yyyyMMdd_HHmmss_fff.log`）。
  同一秒に複数操作をしてもファイル名が衝突して上書きされないようにするため
  （フェーズ4初回検証で判明。接続テストのログも同じ命名に統一）。

## 5.2 メンテナンス切替後の表示更新

メンテナンスモードをON/OFFすると、その場でマシン一覧を読み直して
「メンテ」列のチェックを即座に更新する。

初回実装では、更新処理の先頭に `IsBusy` ガードがあり、メンテナンス操作中
（IsBusy=true）に呼ぶ自動更新が素通りしていた（フェーズ4初回検証で判明・修正済み）。
更新の中核処理をガードの外へ切り出し、メンテナンス切替からは中核処理を直接呼ぶことで
解決した。

- **常駐（統合認証・PID一定 3136）と使い捨て（別資格情報・毎回別PID）が共存**し、
  フェーズ3+の常駐化とフェーズ4の管理操作が安全性を保ったまま同居することを実証。

これをもってフェーズ4は完了と判断する。

## 7.1 本番環境でのフィードバックと対応（2026-08-14 / 0.5.1-alpha）

本番相当の規模で検証した結果、次の指摘を受けて修正した。

| 指摘 | 原因 | 対応 |
|---|---|---|
| マシン一覧が最大500台まで | `MaxRecordCount` に固定値を渡していた | 上限撤廃（0 = 無制限 → `int.MaxValue`） |
| セッション一覧が最大500件まで | 同上 | 同上 |
| デリバリーグループの絞り込みが効かない | **フィルタをDDC側（`-DesktopGroupName`）に渡していた**。完全一致要求で、部分一致も未所属指定も不可 | **全件取得＋クライアント側絞り込み**へ変更。プルダウン化 |
| セッションのユーザー絞り込みが効かない | `-UserName` は `DOMAIN\user` の完全一致要求 | 同上。**部分一致**検索（マシン名も対象） |
| 未所属マシンを絞り込めない | Broker側に「未所属」を表す指定が無い | `(未所属)` 選択肢を追加（該当があるときのみ表示） |
| マシン名で検索したい | 未実装 | マシン名・DNS名の部分一致検索を追加 |
| セッションの状態変更時刻が欲しい | 未取得 | `SessionStateChangeTime` を取得し列とログに追加 |

**設計上の教訓**: Broker コマンドレットの絞り込みパラメータは完全一致が前提で、
運用で求められる「部分一致で探す」「未所属を抽出する」には使えない。
一覧系は**全件取得してクライアント側で絞り込む**方が実用的で、
絞り込み変更のたびに DDC へ問い合わせないぶん応答も速い。

### 性能実測（本番環境）

| 対象 | 件数 | 所要 |
|---|---|---|
| マシン一覧 | 約3,800台 | 約5秒 |
| セッション一覧 | 約1,000セッション | 約1.5秒 |

1台あたり約1.3ミリ秒。所要時間の大半は `Get-BrokerMachine` の通信・転送であり、
上限撤廃による追加コストではない。この規模なら全件取得で実用上問題ないため、
段階読み込み等の複雑化は行わない。

## 8. 本フェーズに含めないもの

- セッション操作（ログオフ・切断・シャドウ）。
- デリバリーグループ／カタログ／ポリシー／タグの操作。
- 常駐Runspace（モジュール再インポートの削減）。
