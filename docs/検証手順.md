# CVAD管理環境での検証手順書

CVAD管理環境（Citrix Studioが入った端末）で実施する検証の**操作手順だけ**をまとめる。
背景・設計・過去の結果は [SPEC_phase1〜3](.) と [README](../README.md) を参照。

このドキュメントは「上から順に実施すれば検証が終わる」ことを目指す。

---

## 0. 準備（毎回共通）

1. 開発端末でビルドした `dist\Release` フォルダを**まるごと**CVAD管理環境へコピーする
   （インストール不要・管理者昇格不要）。フォルダ内には次が入っている:
   - `CitrixAdminTool.exe`（GUI・これを起動する）
   - `CitrixAdminTool.Worker.exe`（GUIが内部で使う。直接起動しない）
   - `CitrixAdminTool.ConsoleTest.exe`（コンソール版）
   - `CitrixAdminTool.Core.dll` ほか
2. `CitrixAdminTool.exe` をダブルクリックして起動する。
3. ログの場所を覚えておく: 画面右上の **「ログフォルダ」** ボタンで開ける。
   実体は `%APPDATA%\CitrixAdminTool\logs\ConnectionTest_yyyyMMdd_HHmmss.log`。
4. 1回のテストごとにログが1本増える。**検証が終わったらこのフォルダのログを
   まとめて開発端末へ持ち帰る**。

> 環境の値は下記の例（CL01 / test.local）で書く。実際のDDC・アカウントに読み替えること。

### ログの読み方（各検証で共通）

| ログ中の表記 | 意味 |
|---|---|
| ヘッダ `プロセス : PID nnnn` | **GUIのPID**。同じGUIを起動したままなら全テストで同じ値 |
| `→ ddc01... OK (..., 1.9s)` | 接続成功。末尾が**所要時間** |
| `→ ddc01... FAILED` の下の `理由:` | 失敗内容 |
| `認証: 統合Windows認証（<user>）` | 統合認証で実行した |
| `認証: 別資格情報（専用プロセス） <account>` | 別資格情報で実行した。使ったアカウント名 |
| `| 接続ワーカー: PID nnnn` | **実際に接続したワーカーのPID**（GUIとは別プロセス） |

**エラーの2種類の見分け**（別資格情報の検証で重要）:
- `呼び出し元はサービスによって認証されませんでした` = **認証**エラー（誰か確立できず）
- `不十分な管理者権限` = **認可**エラー（誰かは分かったが権限不足）

## 検証A: 統合Windows認証の基本接続

**目的**: 現在のログオンユーザーでDDCに接続でき、サイト情報が取れること。

1. GUI左の一覧で **「追加」** をクリック。
2. 右のフォームに入力:
   - ID: `site-a`
   - 表示名: `検証A`
   - プライマリDDC: `ddc01.test.local`
   - 認証モード: **統合Windows認証**
3. **「保存」** をクリック。
4. そのサイトを選んだまま **「接続テスト」** をクリック。

**期待結果**（画面と最新ログ）:
- 一覧の記号が **○**。
- `→ ddc01.test.local ... OK (Site: TESTDDC, Ver: 7.45.1100.0, ...)`
- `認証: 統合Windows認証（TEST\CLAdmin）`

---

## 検証B: フェイルオーバー

**目的**: プライマリDDCが失敗したとき代替DDCへ切り替わること。

1. 検証Aのサイトを編集（または新規追加）:
   - プライマリDDC: `ddc-nonexistent.test.local`（**存在しない名前**）
   - 代替DDC（複数行欄）: `ddc01.test.local`
2. **「保存」** → **「接続テスト」**。

**期待結果**:
- `→ ddc-nonexistent.test.local ... FAILED`
- `→ ddc01.test.local ... OK (...)`
- `** プライマリDDCが失敗したため代替DDCへフェイルオーバーしました。`

---

## 検証C: 別資格情報モード（3ケース）

**目的**: 指定したアカウントが実際に使われ、正しいものは成功・誤ったものは失敗し、
権限の違いが結果に反映されること。**GUIは起動したまま**3ケースを続けて実施する
（同一セッションでも各ケースが正しく区別されることの確認）。

準備: サイトを1つ用意する。
- プライマリDDC: `ddc01.test.local`
- 認証モード: **別の資格情報（接続時に入力）**
- 「保存」しておく。

以下、**「接続テスト」を押すたびに資格情報ダイアログが出る**ので、
ケースごとに指定のアカウントを入力する。

### C-1: 正しい資格情報 → 成功するはず

- ダイアログに **権限のある管理者アカウント**を入力（例: ドメイン `test.local` / ユーザー `Administrator` / 正しいパスワード）。
- **期待**: `→ ddc01.test.local ... OK (...)` ／ `認証: 別資格情報（専用プロセス） test.local\Administrator`

### C-2: 誤った資格情報 → 失敗するはず

- ダイアログに **存在しないユーザー名か誤ったパスワード**を入力（例: ユーザー `Administrator1`）。
- **期待**: `→ ddc01.test.local ... FAILED` ／ 理由 `呼び出し元はサービスによって認証されませんでした`（＝**認証**エラー）。
- ここが成功してしまう場合は不具合（フェーズ2で起きていた挙動）。**失敗が正しい。**

### C-3（任意）: 権限の違う実在アカウント → 認可エラーになるはず

- ダイアログに **実在するがCitrix管理者ロールを持たないアカウント**を入力（例: `test.local\CLUser`）。
- **期待**: `→ ddc01.test.local ... FAILED` ／ 理由 `不十分な管理者権限`（＝**認可**エラー）。
- C-1（成功）・C-2（認証エラー）・C-3（認可エラー）が**3つとも別の結果**になれば、
  指定アカウントが本当に使い分けられている証拠。

**ログで確認する箇所**: 各ログの `認証: 別資格情報（専用プロセス） <account>` が
入力したアカウントと一致していること。

## 検証D: 常駐化の効果測定（フェーズ3+ / 今回の主眼）

**目的**: 統合認証ワーカーが常駐し、2回目以降の接続が速くなること。

準備: 検証Aと同じ**統合Windows認証**のサイト（`ddc01.test.local`）を使う。

1. **GUIを起動したまま**、そのサイトで **「接続テスト」** を実行（**1回目**）。
2. 続けて同じサイトで **「接続テスト」** をもう2回実行（**2回目・3回目**）。
   GUIは閉じない。
3. **「ログフォルダ」** を開き、直近3本のログを比較する。

**期待結果**:

| 見る場所 | 期待 |
|---|---|
| 各ログの `→ ddc01... OK (..., **X.Xs**)` | **1回目が遅く（1.8〜3.3秒）、2回目・3回目が速い（0.3秒前後）** |
| 各ログの `| 接続ワーカー: PID nnnn` | **3本とも同じPID**（＝同じ常駐ワーカーが使い回された） |
| ヘッダの `プロセス : PID` | 3本とも同じ（同じGUI） |

- **2回目以降が明確に速く、かつワーカーPIDが同じ** なら常駐化は成功。
- 参考: 別資格情報（検証C）のログでは `接続ワーカー: PID` が毎回**違う**値になる
  （別資格情報は常駐させず使い捨てのため）。ここが統合認証との違い。

## 検証E（任意）: 標準ユーザー権限での動作

**目的**: ローカル管理者権限のないアカウントでも全機能が動くこと。

- ローカルの Users グループに属する（管理者でない）ADアカウントでWindowsにログオンし、
  検証A〜Dを実施する。昇格プロンプトが出ず、同じ結果になれば合格。
  （2026-08-11に `TEST\CLAdmin` で確認済み。アカウントを変えて再確認する場合のみ。）

## 検証F: マシン一覧の取得（読み取り・フェーズ4）

**目的**: Get-BrokerMachine でマシン一覧が取得・表示できること。

1. メイン画面で、接続できるサイト（例: 統合認証・`ddc01.test.local`）を選ぶ。
2. ツールバーの **「マシン一覧」** をクリック。マシン一覧ウィンドウが開く。
3. ウィンドウ左上の **「更新」** をクリック。

**期待結果**:
- マシンの一覧が表になって出る（メンテ・マシン名・カタログ・デリバリーグループ・
  登録・電源・状態・セッション）。
- ステータス欄に「N 台のマシンを取得しました。（DDC: ...）」。
- 空の場合はマシンが0台か、絞り込み条件に注意（「デリバリーグループ絞り込み」欄）。

別資格情報サイトの場合は、「更新」時に資格情報の入力を1回求められる
（ウィンドウを開いている間は保持され、以降の操作で再入力は不要）。

## 検証G: メンテナンスモード切替（書き込み・フェーズ4）★本番変更

**目的**: Set-BrokerMachine でメンテナンスモードを切り替えられること。

> これは**本番環境を変更する操作**です。検証用マシン、または影響のない対象で行うこと。

1. 検証Fでマシン一覧を表示する。
2. 一覧から対象マシンを1台クリックして選択する。
3. **「メンテナンス ON」**（または OFF）をクリック。
4. 確認ダイアログが出る → 対象マシン名とON/OFFを確認して「はい」。

**期待結果**:
- ステータス欄に「[マシン名] のメンテナンスモードを ON にしました（反映後: ON）。」
- 一覧が自動更新され、対象マシンの「メンテ」列のチェックが変わる。
- 権限が無いアカウント（例: 検証Cの CLUser のようなロールなし）で試すと
  「不十分な管理者権限」で失敗する（＝認可が正しく効いている）。

確認後は元に戻す（ONにしたなら OFF に）ことを忘れずに。

## 検証H: セッション一覧の取得（読み取り・フェーズ4+）

**目的**: Get-BrokerSession でセッション一覧が取得・表示できること。

1. メイン画面でサイトを選び、ツールバーの **「セッション一覧」** をクリック。
2. セッション一覧ウィンドウで **「更新」** をクリック。

**期待結果**:
- セッションの表が出る（ユーザー・マシン・デリバリーグループ・状態・クライアント・開始時刻）。
- ステータス欄に「N 件のセッションを取得しました。」
- ユーザー名・グループで絞り込める（該当ユーザーのセッションを探す用途）。
- テストするには対象サイトに**アクティブなセッションが1つ以上**必要
  （検証用アカウントでVDIにログオンしておく）。

## 検証I: セッションの切断（書き込み・フェーズ4+）★実ユーザー影響

> **実ユーザーのセッションを切断します。検証用アカウントのセッションで行うこと。**

1. 検証Hでセッション一覧を表示する。
2. 対象セッションを1行クリックして選択。
3. **「切断」** をクリック → 確認ダイアログで対象ユーザー・マシンを確認して「はい」。

**期待結果**:
- ステータス欄に「セッション（ユーザー / マシン）を切断しました。」
- 一覧が自動更新され、対象セッションの状態が Disconnected になる（または一覧から消える）。
- Citrix Studio / Director 側でも切断を確認できる。

## 検証J: セッションのログオフ（書き込み・破壊的・フェーズ4+）★作業が失われる

> **対象ユーザーの未保存の作業が失われます。必ず検証用アカウントのセッションで行うこと。**

1. 検証Hでセッション一覧を表示し、対象セッションを選択。
2. **「ログオフ」** をクリック → 「保存されていない作業は失われます」の確認で「はい」。

**期待結果**:
- ステータス欄に「セッション（...）をログオフしました。」
- 一覧が自動更新され、対象セッションが**消える**（セッション終了）。
- Citrix Studio / Director 側でもセッション終了を確認できる。

## 完了後

1. `%APPDATA%\CitrixAdminTool\logs\` のログを**すべて**開発端末へ持ち帰る
   （USBメモリ等。これまでどおり）。
   ※ マシン一覧・メンテナンス切替の詳細は画面のステータス欄と、失敗時のログに出る。
2. どの検証（A〜G）を何回実施したか、ケースごとに何を入力したか（特に検証Cの
   アカウント、検証Gの対象マシン）を控えておくと、持ち帰り後の分析が速い。
