# CVAD GUI管理ツール 仕様書（フェーズ3: 接続ワーカーの分離）

## 0. このドキュメントの位置づけ

フェーズ2で判明した別資格情報モードの不具合
（[SPEC_phase2.md](SPEC_phase2.md) §4.6）の**根本対策**を行う。

原因は「同一プロセス内の認証済み接続の再利用」だった。System.Net / WCF は
`WindowsIdentity` を接続グループの分離キーにしているが、
`LOGON32_LOGON_NEW_CREDENTIALS` はローカル識別子を変えないため、
統合認証と別資格情報でグループが同一とみなされ、接続が使い回されていた。
プロセス内でこれを分離する手段は無い。

したがって **DDCへ接続する処理を、資格情報ごとに別プロセス（ワーカー）へ追い出す。**
本フェーズのスコープはこの分離の確立まで。Broker管理操作は次フェーズ。

---

## 1. アーキテクチャ

```
┌─────────────────────────┐        ┌──────────────────────────────┐
│ CitrixAdminTool.exe     │        │ CitrixAdminTool.Worker.exe   │
│ （GUI / 操作プロセス）   │  起動   │ （接続 / 資格情報ごとに1つ）  │
│                         │──────▶│                              │
│  MainViewModel          │ ファイル│  Program.cs                  │
│  WorkerConnectionService│ 授受    │   CitrixConnectionService    │
│                         │◀──────│    （Core をそのまま利用）    │
└─────────────────────────┘        └──────────────────────────────┘
```

### 1.1 なぜワーカー内は「統合認証」でよいのか

**この設計の要点。**
ワーカープロセス自体を、指定された資格情報のネットワークIDで起動する
（`CreateProcessWithLogonW` + `LOGON_NETCREDENTIALS_ONLY`）。
するとワーカープロセス**全体**がそのネットワークIDを持つため、
ワーカー内では偽装を一切行わず、統合認証（パススルー）として
`Get-BrokerSite` を呼ぶだけでよい。

- プロセス内偽装（フェーズ2の不具合原因）が構造的に不要になる。
- 接続プールはプロセス単位なので、資格情報ごとにプロセスを分ければ
  接続の使い回しは起きない。
- 統合認証のサイトと別資格情報のサイトを同時に開いても、
  それぞれ別プロセスなので互いの接続プールを汚染しない（複数サイト同時接続の要件）。

### 1.2 2つの起動方式

| 認証モード | ワーカーの起動方法 |
|---|---|
| 統合Windows認証 | `System.Diagnostics.Process`（GUIと同じユーザー） |
| 別資格情報 | `CreateProcessWithLogonW`（`LOGON_NETCREDENTIALS_ONLY`） |

`ProcessStartInfo` に UserName/Password を設定する方式は使えない。
それは `LOGON_WITH_PROFILE` 相当で、指定アカウントが実行端末に
**ローカルログオンできる必要がある**（管理用アカウントでは通常不可）。
netonly を使うには `CreateProcessWithLogonW` を直接呼ぶ必要がある。

いずれも標準ユーザー権限で動く（フェーズ2でLogonUser+NEW_CREDENTIALSが
標準ユーザーで動いた事実と整合する。`runas /netonly` 相当）。

## 2. プロセス間のやり取り

**一時ファイルによる受け渡し**とする。

- GUIが入力ファイル（サイト定義のJSON）を書く。
- ワーカーを起動し、引数で入力・出力パスを渡す:
  `CitrixAdminTool.Worker.exe --in <入力> --out <結果>`
- ワーカーは接続テストを行い、結果JSONを出力ファイルへ書いて終了する。
- GUIはワーカーの終了を待ち、出力ファイルを読み、両ファイルを削除する。

### なぜ標準入出力のパイプではなくファイルか

`CreateProcessWithLogonW` で標準出力をキャプチャするには、
匿名パイプを手動生成して `STARTUPINFO` にハンドルを渡す必要があり、
ハンドル継承・クローズの管理が煩雑でバグを生みやすい。
ファイル授受なら統合認証（`Process`）と別資格情報（Win32）で
**受け渡しの仕組みを完全に共通化でき**、パイプ管理が要らない。

置き場所は `%APPDATA%\CitrixAdminTool\tmp\<GUID>.{in,out}.json`。
処理後に必ず削除する。ワーカーはコンソールウィンドウを出さない
（`CREATE_NO_WINDOW`）。タイムアウトを設け、ハングしたワーカーは強制終了する。

### 機密の扱い

- 入力ファイルにはサイト定義（DDCのFQDN等）のみ。**資格情報は書かない**。
- 出力ファイルには接続結果（サイト名・バージョン・エラー文）。使用後削除。
- **パスワードは `CreateProcessWithLogonW` の専用引数だけ**に渡す。
  コマンドライン引数にも一時ファイルにも載せない。
  SecureString から一瞬だけアンマネージドへ展開し、直後にゼロクリアする。
  ワーカー自身はパスワードを一切受け取らない（OSがネットワークIDとして保持）。

## 3. プロジェクト構成の追加分

```
src/CitrixAdminTool.Worker/         (コンソールExe, .NET Framework 4.8)
├── Program.cs                      --in/--out を受けて接続テストし結果を書く
└── Properties/AssemblyInfo.cs

src/CitrixAdminTool.Core/
├── Interop/
│   ├── WorkerProtocol.cs           SiteConnection/結果 ⇔ JSON（ワーカー入出力）
│   └── ProcessLauncher.cs          CreateProcessWithLogonW ラッパー
└── Connection/
    └── WorkerConnectionService.cs  ワーカーを起動し結果を得る（GUIが使う窓口）
```

`ImpersonationAuthenticationContext` は**GUIの通常経路からは使わなくなる**。
プロセス内偽装が不具合の原因だったため。互換のため型は残すが `[Obsolete]` を付す。
`CitrixConnectionService` は変更しない（ワーカー内でそのまま使う）。

## 4. 受け入れ基準（フェーズ3のこのスコープ）

1. GUIが接続テスト時にワーカープロセスを起動し、結果を受け取って表示する。
2. 統合認証のサイトは、GUIと同じユーザーのワーカーで接続できる。
3. 別資格情報のサイトは、`CreateProcessWithLogonW` で起動したワーカーで接続できる。
4. **同一GUIセッションで、統合認証のサイトと別資格情報のサイトを続けて／同時に
   テストしても、後者が前者の接続を再利用しない**（フェーズ2不具合の解消）。
5. 誤った資格情報は、（同一セッションの実行順序によらず）DDC接続時に認証エラーになる。
6. 単一フォルダ自己完結・インストール不要・標準ユーザー権限で動作、を維持する。
7. 資格情報は一時ファイルにもコマンドラインにも現れない。

### 開発端末で検証できること / できないこと

この端末にはCitrix SDKもドメインも無い。したがって:

- 検証できる … ワーカーの起動、入出力ファイルの授受、結果JSONのパース、
  ワーカーが（SDK不在で）失敗した結果をGUIが正しく表示すること、
  `CreateProcessWithLogonW` 経路でワーカーが起動して結果を返すこと。
- 検証できない … 実DDCへの接続、ネットワークIDが実際に切り替わること、
  接続再利用が解消されたこと（受け入れ基準4・5の本体）。
  これらはCVAD管理環境でログを採取して確認する。

## 4.1 観測可能性（フェーズ3初回検証で判明した欠陥と修正）

初回のCVAD検証で、**別資格情報モードで実行したかどうかがログから判別できない**
欠陥が判明した。原因はワーカーが常に統合認証で動くため、ワーカーが返す結果に
「どの資格情報を指定して起動したか」の情報が入らないこと。GUIのログには
すべて「統合Windows認証」と出ていた。

修正: 指定アカウントを知っているのはGUI側だけなので、
`WorkerConnectionService.TestSiteWithCredential` が結果を受け取った後、
各試行に `RequestedIdentity` を刻む。整形出力は
成功・**失敗のどちらでも**「認証: 別資格情報（専用プロセス） <account>」を出す
（認証エラーの切り分けには失敗時こそこの情報が要る）。

この結果、ログを見れば
「この接続は <account> のネットワークIDを持つ専用ワーカーで実行された」
ことが必ず分かる。

## 6. 統合認証ワーカーの常駐化（フェーズ3+ / 実装済み）

初回ウォームアップ（アセンブリロード・JIT・WCFスタック初期化。実測1.8〜3.3秒）は
プロセス単位で一度きり。統合認証は最も使う経路なので、ワーカーを1つ起動したまま
複数リクエストを処理させ、ウォームアップをプロセスごと1回に抑える。

### 6.1 対象は統合認証のみ

別資格情報ワーカーは**常駐させず、従来どおり使い捨て**とする（ユーザー判断）。
理由は、別資格情報の安全性——「都度入力・非永続」と「誤った資格情報は必ず失敗」
（§4.6で実証）——を崩さないため。常駐させると、指定アカウントのネットワークIDを持つ
プロセスがセッション中生き続け、同一アカウントの2回目以降で再入力を省くことになり、
この原則と衝突する。統合認証は実行ユーザー自身なのでこの懸念が無い。

### 6.2 IPC: 名前付きパイプ（GUIがサーバ）

使い捨て時のファイル授受に代えて、常駐ワーカーとは名前付きパイプで
リクエスト／レスポンスを繰り返す。

- **信頼できるGUI側がパイプサーバを所有**する（ワーカーがサーバだと名前の
  横取りの余地がある）。ワーカーは `--serve <パイプ名>` でクライアント接続する。
- パイプは**現在のユーザーのみアクセス可**に制限する（`PipeSecurity`）。
- メッセージは「4バイト長＋UTF-8のJSON本文」でフレーミングする
  （JsonWriterが複数行を出すため改行区切りは使えない）。
- リクエスト `{ "command":"test", "site":{...} }` ／ `{ "command":"quit" }`。
  レスポンスは結果JSON。

### 6.3 ライフサイクル

- 初回の統合認証テストで常駐ワーカーを起動し、以後使い回す
  （`PersistentWorkerClient`）。リクエストはロックで直列化する。
- **クラッシュ回復**: パイプ通信が失敗したらワーカーを作り直して1回リトライする。
- **タイムアウト**: 制限時間を超えたらワーカーを強制終了し、リトライ経路へ。
- **終了**: GUI終了時に `WorkerConnectionService.Dispose()` で quit 送信＋停止。
  GUIが異常終了しても、パイプが切れた時点でワーカーの `--serve` ループが抜けて
  自ら終了する（孤児プロセスを残さない）。

### 6.4 観測可能性

常駐ワーカーはPIDが変わらないため、同一の統合認証テストを繰り返すと
ログの「接続ワーカー: PID」が**同じ値**になる（＝暖まったワーカーの使い回しが見える）。
別資格情報は毎回別PID（使い捨て）。

### 6.5 検証結果

**開発端末**（SDK無し。仕組みの検証）:
- 常駐: 統合認証テストを3回連続 → ワーカーPIDが3回とも同一。
- クラッシュ回復: ワーカーを強制終了 → 次のテストで新PIDに切り替わり結果を取得。
- 終了: `Dispose` 後にワーカープロセスが残らない。
- 別資格情報: 2回実行 → 毎回別PID。常駐ワーカーは増えない。
- GUIを開いて閉じても孤児ワーカーが残らない。

**CVAD環境**（2026-08-11 / CL01・同一GUIセッション。効果の実測）:
- 統合認証ワーカー(PID 896)が約18分間使い回され、初回3.2秒→以降0.1〜0.3秒。
  約20〜30倍の高速化を実測。全実行でワーカーPIDが同一。
- 別資格情報(検証C)はワーカーPIDが毎回変化(7796/1256/5720)、所要1.7〜3.2秒。
  常駐ワーカー(896)には影響せず、安全性を維持したまま共存することを確認。

### 6.6 まだやっていない（さらなる最適化）

`CitrixConnectionService` は接続のたびに Runspace を作り Citrixモジュールを
再インポートしている。常駐ワーカー内で **Runspace自体も保持**すれば、
2回目以降のモジュールインポート分もさらに削れる（仕様書§13の常駐Runspace）。
本フェーズはプロセスレベルの常駐までとし、検証済みの接続コアには手を入れていない。

## 5. 本フェーズに含めないもの

- Broker管理操作（マシン/セッション等）。
- 常駐Runspace（上記 6.6）。
