# CVAD GUI管理ツール 仕様書（フェーズ2: WPF GUIシェル + 別資格情報モード）

## 0. このドキュメントの位置づけ

フェーズ1（[SPEC_phase1.md](SPEC_phase1.md)）で確立した接続層の上に、
WPF (MVVM) のGUIを載せる。対象は仕様書§13が挙げるフェーズ2項目のうち次の2つ:

- WPF (MVVM) GUI。サイト一覧・追加/編集・接続テストボタン・選択中サイト保持。
- 別資格情報モード（LogonUser + impersonation）の実装。

Broker管理操作の追加と常駐Runspace化は本フェーズに含めない（§7参照）。

フェーズ1で確定した前提はすべて引き継ぐ。特に **環境分離**（開発端末にCitrix SDKは無く、
実接続の検証はCVAD管理環境でしか行えない）と **単一フォルダ自己完結・インストール不要** は
フェーズ2でも変更しない。

---

## 1. スコープ

### 1.1 やること

- WPFアプリ `CitrixAdminTool.Wpf`（出力は `CitrixAdminTool.exe`）。
- サイトの一覧表示・追加・編集・削除・保存。
- 選択中サイトの保持（次回起動時に復元）。
- 選択サイト／全サイトの接続テスト（UIをブロックしない非同期実行）。
- サイトごとの接続状態表示（○ / × / … / −）。
- 別資格情報モード（接続の都度入力・非永続）。
- 接続結果のログファイル出力（持ち帰り分析用）。

### 1.2 やらないこと

- Broker管理操作（マシン/セッション、メンテナンスモード、デリバリーグループ、ポリシー、タグ）。
- 常駐Runspace管理への移行（試行ごとの使い捨てのまま）。
- 資格情報の保存・キャッシュ（**恒久的にやらない**）。

## 3. 画面構成

```
┌────────────────────────────────────────────────────────────┐
│ [接続テスト] [全サイト接続テスト] │ [保存] │ [設定フォルダ] [ログフォルダ] │
├──────────────┬─────────────────────────────────────────────┤
│ サイト一覧    │ ┌─ サイト設定 ─────────────────────────────┐ │
│              │ │ ID / 表示名 / プライマリDDC /             │ │
│ ○ 東京本番   │ │ 代替DDC(複数行) / 認証モード              │ │
│   ddc01...   │ └───────────────────────────────────────────┘ │
│ × 大阪DR     │ ┌─ 接続結果 ───────────────────────────────┐ │
│   ddc-dr01.. │ │ （コンソール版と同じ書式のテキスト）      │ │
│              │ └───────────────────────────────────────────┘ │
│ [追加][削除] │                                                │
├──────────────┴─────────────────────────────────────────────┤
│ ステータスメッセージ                            [進捗バー]   │
└────────────────────────────────────────────────────────────┘
```

### 3.1 設計上の判断

**代替DDCは複数行テキスト**（DataGridの行追加ではなく）。
既存の手順書やExcelから貼り付けて一気に流し込める方が実運用に合うため。
改行・カンマ・セミコロン区切りを受け付け、空要素は捨てる。

**接続結果は整形済みテキスト**（構造化ビューではなく）。
検証環境から情報を持ち帰る手段はログファイルであり、
画面に出ているものとログの内容が一致していた方が突き合わせやすい。
そのままコピー＆ペーストできる利点もある。
一覧の状態記号（○×）が一覧性を担うので、ダッシュボードとしての用は足りる。

**未保存の変更は明示する**。タイトルバーに `*` を出し、終了時に確認する。
編集内容を黙って捨てない。なお接続状態の変化（○×）は編集ではないので `*` を立てない。

## 4. 別資格情報モード

### 4.1 なぜ偽装（impersonation）なのか

Brokerコマンドレットの多くは汎用的な `-Credential` を持たない。
そのためコマンドレットに資格情報を渡すのではなく、`LogonUser` で取得したトークンによる
偽装コンテキスト内でRunspaceごと実行する。
WinRMリモーティングは使わない（DDC側に追加構成を強いるため）。

これはフェーズ1で `IAuthenticationContext` として先に抽象化してあった箇所であり、
`CitrixConnectionService` は既にこの抽象越しに動いていたため、
接続層のロジック自体は変更していない。

### 4.2 なぜ LOGON32_LOGON_NEW_CREDENTIALS なのか

`runas /netonly` と同じ挙動で、**ローカルの識別子は現在のユーザーのまま維持し、
外向きのネットワーク認証だけ**を指定した資格情報で行う。

- 目的は「別のADアカウントでDDCに認証すること」だけで、ローカルログオン権限は不要。
- `LOGON32_LOGON_INTERACTIVE` だと対象アカウントが実行端末にローカルログオンできる
  必要があり、管理用アカウントではポリシーで禁止されていることが多い。

**副作用として、資格情報の正しさはローカルでは検証されない**。
`LogonUser` はパスワードが誤っていても成功し、実際にDDCへ接続した時点で初めて
認証エラーになる。UIはこの前提で案内する。

**特権を必要としない**（2026-08-10 実環境で確認）。
`LogonUser` は `SeTcbPrivilege`（オペレーティング システムの一部として機能）を
要求するという理解をされることがあるが、`LOGON32_LOGON_NEW_CREDENTIALS` では不要。
ローカル管理者権限を持たない標準ドメインユーザー（Usersグループ）で
別資格情報モードの接続が成功することを実証済み。
本モードのために運用担当者の端末へ特権を与える必要はない。

### 4.3 認証したアカウントの表示（2026-08-11 改訂）

`LOGON32_LOGON_NEW_CREDENTIALS` では偽装中でも `WindowsIdentity.GetCurrent()` は
**元のユーザー名を返す**。当初はこれを避けるため、`GetEffectiveUserName()` が
**入力された資格情報のアカウント名**を返す実装にしていた。

**これは誤りだった。** 入力値をそのまま「認証:」として表示していたため、
偽装が効いていようがいまいが同じ表示になり、**検証不能**になっていた。
実際、存在しないアカウント名でも「認証: そのアカウント」と表示されたまま
接続が成功していた（§4.6）。

現在は次の方針に改めている。

- `AuthenticatedAs` … プロセスの実行ユーザー。**確認できた事実**。
- `RequestedIdentity` … 別資格情報モードで**指定された**アカウント名。事実ではない。
- `ImpersonationActive` … コマンドレット実行時にスレッド偽装トークンが有効だったか。
  `WindowsIdentity.GetCurrent(true)` が null か否かで判定する
  （ローカル識別子が変わらないため、名前の比較では判別できない）。

報告ではこの3つを区別して出し、
「DDCが実際にどちらのアカウントを認証したかは確認できない」ことを明示する。

**教訓** … 「偽らないための表示」を意図した実装が、
かえって検証できない表示を作ることがある。
確認できた事実と、こちらの意図にすぎない値は、必ず分けて記録する。

### 4.6 未解決の不具合: 指定した資格情報が使われない（調査中）

2026-08-11の検証で、**存在しないアカウント名を入力しても接続が成功する**ことが判明した。
実際にはプロセスの実行ユーザーで認証されていたと考えられる。

否定された仮説 … 「PowerShellのパイプラインが別スレッドで動くため偽装が引き継がれない」。
ローカル再現テストの結果、パイプラインは別スレッドで動くが
.NETのExecutionContextが偽装を伝播しており、偽装はコマンドレットまで届いていた。
（それでも実行位置を推測に頼らないよう、`Runspace.ThreadOptions` は
`UseCurrentThread` に固定した。）

**確定した原因（2026-08-11 切り分けテスト完了）** … **プロセス内の認証済み接続の再利用**。

切り分けテスト「プロセスを完全に終了 → 新規起動して最初の操作として
誤った資格情報で接続」を実環境で実施した結果、**期待どおり認証エラーで失敗した**
（`SecurityNegotiationException`「呼び出し元はサービスによって認証されませんでした」）。
また、Citrix管理者ロールの無いアカウント（統合認証）が「不十分な管理者権限」で
認可拒否された直後に、別資格情報のAdministrator指定で成功しており、
資格情報が実際にDDCへ届く場合の権限分離も実証された。つまり:

- 新規プロセスでは、指定した資格情報が実際にDDCへのネットワーク認証に使われる
  （誤っていれば失敗する）。偽装のメカニズム自体は機能している。
- 同一プロセス内で先に別のアカウント（統合認証を含む）で接続していると、
  その認証済み接続が再利用され、後から指定した資格情報が無視される。
- `LOGON32_LOGON_NEW_CREDENTIALS` はローカル識別子を変えないため、
  System.Net / WCF の接続グループ分離が効かず、プロセス内での回避は困難。

### 4.7 修正方針: 接続プロセスの分離（フェーズ3で実装）

**操作するプロセス（GUI）と、DDCへ接続するプロセスを分ける。**

- GUI本体はSDKを直接呼ばず、接続専用の子プロセス（ワーカー）に委譲する。
- ワーカーは**資格情報（＝認証コンテキスト）ごとに1プロセス**とする。
  統合認証用と、別資格情報のアカウントごとに独立のワーカーを持つ。
  これにより認証済み接続の再利用がプロセス境界で自然に分離される。
- **複数サイトへの同時接続を前提に設計する**（運用要件）。
  サイトAは統合認証・サイトBは別アカウント、といった併用が
  互いの接続プールを汚染しない構成にする。
- 副次的な利点:
  - ワーカーを常駐させれば、そのまま常駐Runspace化（§7）になる。
    初回ウォームアップ（実測1.8〜3.3秒）もプロセスごと1回で済む。
  - 資格情報はワーカー起動時に渡して以後ワーカー内に閉じるため、
    GUI側のメモリに保持し続けない。
- 実装候補: 子プロセスを `CreateProcessWithLogonW`（`LOGON_NETCREDENTIALS_ONLY`）で
  起動する方式か、通常起動した子プロセス内で `LogonUser` + 偽装する方式。
  前者はプロセス全体が指定資格情報のネットワークIDを持つため確実性が高い。
  GUIとワーカー間は標準入出力または名前付きパイプでやり取りする。

それまでの間、別資格情報モードは「同一プロセスで先に他の接続をしていない場合のみ
正しく動く」状態であり、**権限分離が必要な用途には使わない**。

### 4.4 資格情報の扱い

- `PasswordBox.SecurePassword` から `SecureString` のまま取り出し、
  マネージドな `string` には一度も変換しない。
- `LogonUser` に渡す一瞬だけ `Marshal.SecureStringToGlobalAllocUnicode` で
  アンマネージドへ展開し、`finally` で `ZeroFreeGlobalAllocUnicode` によりゼロクリアする。
- 保持するのはトークン（`SafeAccessTokenHandle`）のみで、接続完了後に `Dispose` する。
- **どこにも永続化しない**。`sites.json` に保存されるのは `authMode` だけ。

### 4.5 資格情報を渡し忘れたときの扱い

`CitrixConnectionService.TestSiteConnection(site, auth)` に `auth = null` を渡し、かつ
サイトが `PromptForCredential` の場合、**黙って統合認証にフォールバックしない**。
誰の権限で操作したのかを偽ることになるため、失敗として報告する。
コンソール版（統合認証のみ対応）はこの経路を通る。

## 5. 設定ファイルの保存先

| 版 | 保存先 |
|---|---|
| GUI版 | `%APPDATA%\CitrixAdminTool\sites.json`（仕様書§9.2） |
| コンソール版 | 実行フォルダ直下の `sites.json`（第1引数で上書き可） |

両方を同じフォルダに同梱するため保存先が食い違う。
GUI版は起動時、ローミング側が無ければ**実行フォルダ側の `sites.json` を読み込む**
（フェーズ1で作った設定を手で移し替えさせないため）。
このとき未保存状態にして、保存すればローミング側に書かれることを明示する。

UI状態（選択中サイト）は `%APPDATA%\CitrixAdminTool\ui-state.json` に分けて保存する。
`sites.json` は環境間で配って回る「設定」であり、端末限りの使い勝手情報を混ぜると
設定の受け渡しが煩雑になるため。

ログは `%APPDATA%\CitrixAdminTool\logs\ConnectionTest_yyyyMMdd_HHmmss.log`。

## 6. ビルド環境上の追加事項

WPFのアセンブリ（`PresentationFramework` / `PresentationCore` / `WindowsBase` / `System.Xaml`）は、
ターゲティングパックが無い環境では既定の参照解決では見つからない。
実体が .NET Framework ランタイム配下の `WPF\` サブフォルダにあるため。

そこで csproj で明示的に `HintPath` を指定し、`Private=false`（コピーローカルしない）とする。
いずれも .NET Framework 4.8 に同梱されるシステムアセンブリなので、
単一フォルダ自己完結の要件は損なわれない。

XAMLのマークアップコンパイルは `Microsoft.WinFx.targets` 経由で
`PresentationBuildTasks.dll` が担う。どちらもランタイム配下に存在するため、
NuGetを追加せずにビルドできることを確認済み。

## 7. フェーズ3以降

- Broker管理操作の段階的追加（マシン/セッション、メンテナンスモード、
  デリバリーグループ、ポリシー、タグ等）をモジュール単位・プラグイン的に拡張。
- 常駐Runspace管理への移行。
  フェーズ1の実測で、同一プロセス内の1回目が1.8〜3.2秒、2回目以降が0.3秒という差が出ている。
  所要時間の大半は初回のウォームアップ（アセンブリロード・JIT・WCFスタック初期化）であり、
  操作を連続実行するGUIでは常駐化の効果が見込める。
  ただし検証済みの接続層に手を入れることになるため、GUIシェルの検証を通してから着手する。
